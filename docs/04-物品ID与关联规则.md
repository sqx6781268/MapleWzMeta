# 04 · ID 归一与跨源关联规则

这是整个项目的**核心规则**：同一个物品的名称与属性来自不同 `.wz` 包，且层级不一致，
只有先把 ID 归一到同一形态，才能对齐。

## 1. 三层规则总览

| 层 | 规则 | 实现 |
|---|---|---|
| 识别 | 名字是 **7 或 8 位纯数字**的 `imgdir` 才是实体节点；不依赖固定层级 | `extract.LooksLikeItemID`（`internal/extract/extract.go:39`） |
| 归一 | 去掉 `.img` 后缀 → 纯数字则**零填充到 8 位**；非纯数字原样返回 | `extract.NormalizeID`（`internal/extract/extract.go:27`） |
| 合并 | 以 `(lang, id)` 为主键，名称侧与属性侧各自 upsert，**互不覆盖对方字段** | `store.PutNames` / `store.PutInfos` |

零填充是必须的：`String.wz` 写 7 位 `4000000`（`Eqp` 表甚至丢掉前导零写作 `1010000`），
`Item.wz`/`Character.wz` 写 8 位 `04000000`，不补齐就对不上。

## 2. 各来源的层级差异（实测）

| 来源 | 根 imgdir | 到 ID 节点的路径 | ID 位数 | 侧 |
|---|---|---|---|---|
| `String.wz/Cash.img.xml` | `Cash.img` | 根 → **ID** | 7 | 名称 |
| `String.wz/Consume.img.xml` | `Consume.img` | 根 → **ID** | 7 | 名称 |
| `String.wz/Ins.img.xml`、`Pet.img.xml` | 同名 | 根 → **ID** | 7 | 名称 |
| `String.wz/Etc.img.xml` | `Etc.img` | 根 → `Etc` → **ID** | 7 | 名称 |
| `String.wz/Eqp.img.xml` | `Eqp.img` | 根 → `Eqp` → 部位 → **ID** | 7 | 名称 |
| `Item.wz/<类别>/<系列>.img.xml` | 如 `0430.img` | 根 → **ID** → `info` | 8 | 属性 |
| `Character.wz/<部位>/<id>.img.xml` | 如 `01002936.img` | **根即 ID** → `info` | 8 | 属性 |
| `Character.wz/<id>.img.xml`（根级 18 个） | 如 `00002000.img` | 同上，但**无类别目录** | 8 | 属性 |

> 上表只列**物品相关**的来源。`String.wz` 目录下另有 `Mob`/`Npc`/`Skill`/`Map`/`MonsterBook`/`PetDialog`
> 等别的实体域的文本表，它们目前**也会被当成名称侧**——这是个已知缺陷，见 §7 末尾与
> [09-验证基线与已知缺陷](09-验证基线与已知缺陷.md) §5；20 张表各自的位数形态、归属实体与实测关联率见
> [附录-实体与String.wz的关联](附录-实体与String.wz的关联.md)。

要点：

- **名称侧走 `extract.Names`（全树 `Walk`）**，因为层级不固定；
  命中条件：`imgdir` + 名字像 ID + 有 `string` 型 `name` 子节点（`internal/extract/extract.go:70`）。
- **属性侧走 `extract.Infos`（只看根的下一层）**，但 `Character.wz` 特判：一个文件 = 一个物品，
  根名即 ID（`internal/extract/extract.go:117`）。
- 分流发生在管线层：相对路径以 `String.wz` 开头 → 名称侧，否则 → 属性侧（`internal/scan/scan.go:240`）。

## 3. 名称侧抽取规则

对每个命中的 ID 节点：

| 子节点 | 归入 | 规则 |
|---|---|---|
| `name`（`string`） | `NameEntry.Name` | **必需**，没有就整条跳过 |
| `desc`（`string`） | `NameEntry.Desc` | 可选 |
| 其余 `string` | `NameEntry.Extra[key]` | 排除 `name`/`desc`；当前**不入库**，仅内存视图 |
| 非 `string` 类型 | 忽略 | |

`Category` 由父节点名推断（`categoryOf`，`internal/extract/extract.go:177`）：
父节点是文件根（名字以 `.img` 结尾）或父节点本身也是 ID → 返回**空串**；
否则返回分层目录名（`Accessory`、`Etc` 等）。

## 4. 属性侧抽取规则

`InfoEntry.Info` 由 `flattenScalars(info)` 得到（`internal/extract/extract.go:143`），规则：

| `info` 下的子节点 | 扁平化结果 |
|---|---|
| 标量（`int`/`string`/`short`/`double`/…） | `key = value` |
| `canvas` / `vector` | 自身属性 → `icon.width`；子节点属性 → `icon.origin.x`（点号拼路径） |
| `imgdir` | **跳过**（嵌套结构不进 info） |
| `info` 节点自身的扩展属性 | 加 `@` 前缀，如 `@indent` |

另外记录：

- `Parts = node.ChildNames()` —— ID 节点下除 `info` 外的兄弟节点名（`default`/`walk1`/`attack`…），用来判断外观数据完整度；
- `HasInfoDir` —— 是否存在 `info` 子节点；**只有它为真才置 `has_info = 1`**。

入库前过滤：`len(Info) == 0` 的条目直接丢弃（`internal/scan/scan.go:246`），避免空属性行覆盖已有名称。

## 5. 分类（category）取值与优先级

两侧都能提供 `category`，规则是**先写入者占位，空值不覆盖**：

| 来源 | 取值方式 | 例子 |
|---|---|---|
| `String.wz` | 分层目录名（`categoryOf`） | `Accessory`、`Etc` |
| `Item.wz` / `Character.wz` | 相对路径的**次级目录名**（`categoryOfDir`） | `Consume`、`Cap` |
| 文件直挂在 `.wz` 根下 | **空串** | `Character.wz/00002000.img.xml` |

SQL 侧对应 `category = CASE WHEN item.category = '' THEN excluded.category ELSE item.category END`
（`internal/store/store.go:325`）—— 注意是"库内为空才填"，即**先入者胜出**，不是后入者覆盖。

> **禁止把 `-`、`N/A` 这类哨兵值写进库**。`categoryOfDir` 在无类别层时返回空串（`internal/extract/extract.go:197`），
> 展示层再翻译成"(未分类)"（`internal/store/store.go:581`）。

## 6. 合并语义（为什么两侧不互相覆盖）

一个 ID 可能先被 `Item.wz` 写入、后被 `String.wz` 写入，也可能只有单边。三条不变量：

1. **名称侧不碰 `info`**：`PutNames` 的 UPSERT 只更新 `name/descr/category/has_name`。
2. **属性侧不碰 `name/descr`**：`PutInfos` 只更新 `info/category/has_info`。
3. **空值不覆盖已有非空值**：`name = CASE WHEN excluded.name <> '' THEN excluded.name ELSE item.name END`。

`info` 内部是**按 key 合并**而非整体替换：`mergeInfo`（`internal/store/store.go:388`）先 `SELECT` 旧 JSON、
反序列化、`for k,v := range add` 覆盖、再序列化写回。因此同一 ID 从多处补属性会累积。

名称为空（`strings.TrimSpace(a.Name) == ""`）的条目**不写入也不计数**（`internal/store/store.go:333`）。

## 7. 非物品域 ID 的处理

`NormalizeID` 对非纯数字原样返回，`LooksLikeItemID` 只认 7/8 位，因此下面这些**不会从自己的包进物品表**：

| 域 | ID 形态 | 若强行入库的后果 |
|---|---|---|
| `Map.wz` | 9 位（`000000000`） | 与物品号段冲突 |
| `Mob.wz`、`Npc.wz`（立绘包） | 7 位 | 与物品 7 位号段**真实冲突**（如 Npc `0002000` vs 消耗品 `02000`） |
| `Skill.wz` | 4 段分组 | 名字非数字 |
| `Character.wz/Afterimage` | 英文（`swordOS`） | 非数字 |

> ⚠️ **但这道闸门只认 ID 形态、不认实体域。** `sources` 里的 `String.wz` 是按**目录整体**扫的，
> 其中的 `Mob.img.xml`、`Npc.img.xml`、`Skill.img.xml` 用的正是**怪物 / NPC / 技能的 7 位 ID**，
> 形态上完全符合"像物品 ID"，于是它们的 `name` 会作为**物品名称**入库。
> 实测约 **4,165 条**（Mob 2,002 + Npc 1,803 + Skill 360），占名称条目 28,262 的约 15%。
> 典型案例、量化口径与修复方案见 [09-验证基线与已知缺陷](09-验证基线与已知缺陷.md) §5。

图标索引稍宽：`internal/icons/icons.go:59` 除物品 ID 外，还接受 1~12 位纯数字（`idRe`），
因此 Npc 图标能被索引，但只在查询时按物品 ID 命中。

> 将来若要做 NPC/怪物检索，**另立实体表**（如 `npc`、`mob`），不要复用 `item`；
> 名称侧也应顺势按表名白名单只认物品类文本表。

## 8. 检索侧的 ID 兼容

用户手输的常是**原始 7 位号段前缀**（如 `4000`），库里存的是 8 位补零形式，因此
`Query.IDPrefix` 会**同时**查 `4000*` 和 `04000*` 两个区间（`internal/store/store.go:690`）：

```sql
(id >= '4000' AND id < '4001') OR (id >= '04000' AND id < '04001')
```

区间上界由 `prefixUpper`（`internal/store/store.go:728`）逐字节加一求得，用 `>= / <` 而非 `LIKE`，
以便走主键索引。`Query.ID` 则是**精确匹配、不做补零**——传 `4000000` 查不到 `04000000`，
调用方需自己补齐 8 位（或改用 `q=` 关键字参数，见 [08-命令行与查询接口](08-命令行与查询接口.md)）。

## 9. 验证过的对齐证据

- 全量扫描 45,592 个 XML，**解析失败 0**。
- 关联结果 56,264 个唯一 ID，其中 **22,963 条双向命中**（既有名称又有属性）——
  这个数量级本身即证明"7 位补零到 8 位"的对齐规则正确。
- 缺名称 28,568 条集中在 `Hair`(15,234)、`Face`(9,555)，属 `String.wz` **导出范围**缺口，
  不是解析或对齐缺陷（详见 [09-验证基线与已知缺陷](09-验证基线与已知缺陷.md)）。
