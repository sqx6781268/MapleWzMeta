# 04 · ID 归一与跨源关联规则

这是整个项目的**核心规则**：同一个实体的名称与属性来自不同 `.wz` 包，且层级不一致，
只有先把 ID 归一到同一形态、并判定它属于哪个实体域，才能对齐。
物品 / NPC / 怪物三个域共用这套规则，差别只在**来源集合**与**位数门槛**上。

## 1. 三层规则总览

| 层 | 规则 | 实现 |
|---|---|---|
| 定域 | 名称侧按 `String.wz` 表名白名单 `nameTables` 判域；属性侧按包名（`Mob.wz`→mob、`Npc.wz`→npc、其余→item）判域 | `extract.NameKindOf`（`internal/extract/extract.go:77`）/ `extract.KindOf`（`internal/extract/extract.go:77`） |
| 识别 | 在该域的**位数形态内**的纯数字 `imgdir` 才是实体节点；不依赖固定层级 | `extract.LooksLikeID`（`internal/extract/extract.go:117`） |
| 归一 | 去掉 `.img` 后缀 → 纯数字则**零填充到 8 位**；非纯数字原样返回 | `extract.NormalizeID`（`internal/extract/extract.go:33`） |
| 合并 | 以 `(lang, id)` 为主键、按 `Kind` 进各自的表，名称侧与属性侧各自 upsert，**互不覆盖对方字段** | `store.PutNames` / `store.PutInfos` |

零填充是必须的：`String.wz` 写 7 位 `4000000`（`Eqp` 表甚至丢掉前导零写作 `1010000`、发型脸型写作 5 位），
`Item.wz`/`Character.wz` 写 8 位 `04000000`，`Mob.wz` 文件名一律 7 位、`String.wz/Mob` 同一怪物却写 `21`——
只有都补齐到 8 位才能跨源、跨两侧对齐。

**各域的位数形态不同**（实测，`LooksLikeID`）：

| 域 | 合法位数 | 说明 |
|---|---|---|
| 物品 | 7 或 8 位；**`String.wz/Eqp` 表单独放行 5 位** | Hair/Face 的名称在 `Eqp` 里就是 5 位，实测 22,691 条，不放行会整批丢弃（修复前缺陷，见 [附录](附录-实体与String.wz的关联.md) §5） |
| NPC / 怪物 | 1~8 位纯数字皆可 | `Mob.wz`/`Npc.wz` 文件名补零到 7 位，而 `String.wz/Mob`、`String.wz/Npc` 里同一实体可能写成 2~6 位（如 `21`），两侧都要认，位数无统一上界 |

## 2. 各来源的层级差异（实测）

| 来源 | 根 imgdir | 到 ID 节点的路径 | ID 位数 | 域 / 侧 |
|---|---|---|---|---|
| `String.wz/Cash.img.xml` | `Cash.img` | 根 → **ID** | 7 | item / 名称 |
| `String.wz/Consume.img.xml` | `Consume.img` | 根 → **ID** | 7 | item / 名称 |
| `String.wz/Ins.img.xml`、`Pet.img.xml` | 同名 | 根 → **ID** | 7 | item / 名称 |
| `String.wz/Etc.img.xml` | `Etc.img` | 根 → `Etc` → **ID** | 7 | item / 名称 |
| `String.wz/Eqp.img.xml` | `Eqp.img` | 根 → `Eqp` → 部位 → **ID** | 7 / **5** | item / 名称 |
| `String.wz/Mob.img.xml` | `Mob.img` | 根 → **ID** | 7 / 6 / 2 | mob / 名称 |
| `String.wz/Npc.img.xml` | `Npc.img` | 根 → **ID** | 7 / 5 / 4 / 3 | npc / 名称 |
| `Item.wz/<类别>/<系列>.img.xml` | 如 `0430.img` | 根 → **ID** → `info` | 8 | item / 属性 |
| `Item.wz/Pet/<id>.img.xml` | 如 `5000000.img` | **根即 ID** → `info` | 7 | item / 属性 |
| `Character.wz/<部位>/<id>.img.xml` | 如 `01002936.img` | **根即 ID** → `info` | 8 | item / 属性 |
| `Character.wz/<id>.img.xml`（根级 18 个） | 如 `00002000.img` | 同上，但**无类别目录** | 8 | item / 属性 |
| `Mob.wz/<id>.img.xml`、`Npc.wz/<id>.img.xml` | 如 `0000021.img` | **根即 ID** → `info` | 7 | mob·npc / 属性 |
> 名称侧走的是 `String.wz` 的**表名白名单**（`nameTables`，`internal/extract/extract.go:77`）：
> `Cash`/`Consume`/`Eqp`/`Etc`/`Ins`/`Pet` 归物品，`Mob`/`Npc` 归对应实体域，**其余表整张跳过**。
> 修复前是"路径以 `String.wz` 开头就算名称侧"，于是 `Mob`/`Npc`/`Skill` 三张别的实体的名字
> 被写进了物品行（实测 4,347 条跨实体污染，见 [附录](附录-实体与String.wz的关联.md) §4 与本文 §7）。
> `Skill`/`Map`/`MonsterBook`/`PetDialog`/`ToolTipHelp` 目前不入库。20 张表各自的位数形态、归属实体与实测关联率见
> [附录-实体与String.wz的关联](附录-实体与String.wz的关联.md)。

要点：

  有 `string` 型 `name` 子节点（`internal/extract/extract.go:158`）。**命中后不再向下递归**：
  怪物/NPC 条目内部有 `0`/`1` 这类数字子节点（动画帧、对话分支），继续下钻就把它们当成了新实体。
  由 `extract.RootID`（`internal/extract/extract.go:322`）判定：**文件名（去 `.xml`/`.img`）与根 imgdir 名同为数字 ID
  且位数 ≥7** 即成立，覆盖 `Character.wz`、`Mob.wz`、`Npc.wz` 与 `Item.wz/Pet`
  （修复前只对 `Character.wz` 开特判，导致 `Item.wz/Pet` 的 357 个宠物文件属性整批漏抽，见 [附录](附录-实体与String.wz的关联.md) §3）；
- 分流发生在管线层：相对路径在 `String.wz` 下走名称侧（`internal/scan/scan.go:330`），否则走属性侧（`internal/scan/scan.go:342`），
  两侧各自再定实体域 `Kind`。

## 3. 名称侧抽取规则

对每个命中的 ID 节点：

| 子节点 | 归入 | 规则 |
|---|---|---|
| `name`（`string`） | `NameEntry.Name` | **必需**，没有就整条跳过 |
| `desc`（`string`） | `NameEntry.Desc` | 可选 |
| 其余 `string` | `NameEntry.Extra[key]` | 排除 `name`/`desc`；当前**不入库**，仅内存视图 |
| 非 `string` 类型 | 忽略 | |
`Category` 由父节点名推断（`categoryOf`，`internal/extract/extract.go:293`）：
父节点是文件根（名字以 `.img` 结尾）或父节点本身也是 ID → 返回**空串**；
否则返回分层目录名（`Accessory`、`Etc` 等）。

## 4. 属性侧抽取规则
`InfoEntry.Info` 由 `flattenScalars(info)` 得到（`internal/extract/extract.go:251`），规则：

| `info` 下的子节点 | 扁平化结果 |
|---|---|
| 标量（`int`/`string`/`short`/`double`/…） | `key = value` |
| `canvas` / `vector` | 自身属性 → `icon.width`；子节点属性 → `icon.origin.x`（点号拼路径） |
| `imgdir` | **跳过**（嵌套结构不进 info） |
| `info` 节点自身的扩展属性 | 加 `@` 前缀，如 `@indent` |

另外记录：

- `Parts = node.ChildNames()` —— ID 节点下除 `info` 外的兄弟节点名（`default`/`walk1`/`attack`…），用来判断外观数据完整度；
- `HasInfoDir` —— 是否存在 `info` 子节点；**只有它为真才置 `has_info = 1`**。
入库前过滤：`len(Info) == 0` 的条目直接丢弃（`internal/scan/scan.go:345`），避免空属性行覆盖已有名称。

## 5. 分类（category）取值与优先级

两侧都能提供 `category`，规则是**先写入者占位，空值不覆盖**：

| 来源 | 取值方式 | 例子 |
|---|---|---|
| `String.wz` | 分层目录名（`categoryOf`） | `Accessory`、`Etc` |
| `Item.wz` / `Character.wz` | 相对路径的**次级目录名**（`categoryOfDir`） | `Consume`、`Cap` |
| 文件直挂在 `.wz` 根下 | **空串** | `Character.wz/00002000.img.xml` |
| NPC / 怪物 | 恒为**空串** | `Mob.wz`、`Npc.wz` 一文件一实体，没有分类目录 |
| `Character.wz` **根级文件** | 按 `info.islot` 反推（`rootCategory`） | 实测 18 个根级文件只有 `Bd`→`BodySkin`（身体皮肤）、`Hd`→`HeadSkin`（头部皮肤） |

（`internal/store/store.go:416` `putNamesSQL`）—— 注意是"库内为空才填"，即**先入者胜出**，不是后入者覆盖。
> **禁止把 `-`、`N/A` 这类哨兵值写进库**。`categoryOfDir` 在无类别层时返回空串（`internal/extract/extract.go:313`），
> 展示层再翻译成"(未分类)"（`store.NoCategoryName`，`internal/store/store.go:35`）。

## 6. 合并语义（为什么两侧不互相覆盖）

一个 ID 可能先被 `Item.wz` 写入、后被 `String.wz` 写入，也可能只有单边。三条不变量：

1. **名称侧不碰 `info`**：`PutNames` 的 UPSERT 只更新 `name/descr/category/has_name`。
2. **属性侧不碰 `name/descr`**：`PutInfos` 只更新 `info/category/has_info`。
3. **空值不覆盖已有非空值**：`name = CASE WHEN excluded.name <> '' THEN excluded.name ELSE item.name END`。
`info` 内部是**按 key 合并**而非整体替换：`mergeInfo`（`internal/store/store.go:514`）先 `SELECT` 旧 JSON、
反序列化、`for k,v := range add` 覆盖、再序列化写回。因此同一 ID 从多处补属性会累积。
名称为空（`strings.TrimSpace(a.Name) == ""`）的条目**不写入也不计数**（`internal/store/store.go:446`）。

## 7. 三个实体域为何必须分表

物品 / NPC / 怪物三个域的 ID 补零到 8 位后**整体落在同一个号段空间**——同一条 `01110100` 既是"绿蘑菇戒指"
（物品）也是"绿色水灵菇"（怪物）。实测重叠面（口径：各包 `<imgdir name="数字">` 键补零后与库内物品 ID 逐一比对）：

| 域 | 该域条目 | 与物品 ID 重叠 |
|---|---|---|
| `Mob.wz` / `String.wz/Mob` | 2,379 / 2,002 | **2,002（100%）** |
| `Npc.wz` / `String.wz/Npc` | 7,506 / 1,803 | **1,803（100%）** |

（数字来自 [附录](附录-实体与String.wz的关联.md) §4、§6 的实测统计。）

因此**不能把三个域塞进同一张 `item` 表**——同 ID 就会互相覆盖名称与属性，正是修复前的
4,347 条跨实体污染（名称侧不辨域、怪物/NPC/技能的名字写进物品行）。解决办法是两层同时做：

1. **名称侧按表名白名单定域**（`nameTables`）：`String.wz/Mob`、`/Npc` 的名字归到怪物 / NPC 域，
   不再混进物品域；不在白名单里的表整张跳过。
2. **入库按 `Kind` 分表**：`item` / `npc` / `mob` 三张列结构完全一样的表，各域各写各的
   （表结构见 [06](06-数据模型与存储规则.md) §2）。

其余不入库的域，仍靠"位数形态 + 非数字名"自然挡住：

| 域 | ID 形态 | 归宿 |
|---|---|---|
| `Map.wz` | 9 位（`000000000`） | 未登记进 `nameTables`，且 `sources` 不含 `Map.wz`，不入库 |
| `Skill.wz` | 7/8 位 + 3/4 段分组 | 目前不入库；要接就在 `Kinds` 加一个域并登记 |
| `Character.wz/Afterimage` | 英文（`swordOS`） | 非纯数字，识别层直接跳过 |
图标也按域取用（`entityDomains`，`internal/icons/icons.go:34`），物品域只认 `{Item, Character}` 目录，
拿不到 `Npc`/`Mob` 目录里的立绘（修复前实测 1,578 个物品行挂了 NPC 图）。
NPC / 怪物域的检索与解析细节见 [11-NPC与怪物解析](11-NPC与怪物解析.md)。

## 8. 检索侧的 ID 兼容
- **`id` / `q`（纯数字）一律走 `extract.NormalizeID` 补零**（`Query.clauses`，`internal/store/store.go:849`）：
  怪物原生 7 位，用户手输 `1110100` 也能命中库里的 `01110100`；`Query.ID` 精确匹配前会先补齐 8 位。
- 用户手输的常是**原始 7 位号段前缀**（如 `4000`），库里存的是 8 位补零形式，因此
  `Query.IDPrefix` 会**同时**查 `4000*` 和 `04000*` 两个区间：

```sql
(id >= '4000' AND id < '4001') OR (id >= '04000' AND id < '04001')
```
区间上界由 `prefixUpper`（`internal/store/store.go:918`）逐字节加一求得，用 `>= / <` 而非 `LIKE`，
以便走主键索引。检索前还要先选对实体域（`Query.Kind` / HTTP `?kind=`），否则会到错的表里查。

## 9. 验证过的对齐证据

> 下列为**物品域修复前**的基线（口径：仅 `String.wz`+`Item.wz`+`Character.wz` 三个源、旧名称侧不分流）；
> 白名单定域与 5 位放行后 Hair/Face 补齐名称、怪物/NPC 移出物品表，物品域"有名称/齐全"数会**先降后升**。
> 各域当前的实测规模以 [09-验证基线与已知缺陷](09-验证基线与已知缺陷.md) 与 [11-NPC与怪物解析](11-NPC与怪物解析.md) 为准。

- 全量扫描 45,592 个 XML，**解析失败 0**。
- 关联结果 56,264 个唯一 ID，其中 **22,963 条双向命中**（既有名称又有属性）——
  这个数量级本身即证明"7 位补零到 8 位"的对齐规则正确。
- 缺名称 28,568 条集中在 `Hair`(15,234)、`Face`(9,555），其中 22,691 条是**位数门槛**误伤（`Eqp` 5 位键，现已放行），
  剩下的才是 `String.wz` 导出范围真缺口（详见 [09-验证基线与已知缺陷](09-验证基线与已知缺陷.md)）。
