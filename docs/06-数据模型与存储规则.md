# 06 · 数据模型与存储规则

库：`data/mia.db`（SQLite，WAL 模式）。实现全部在 `internal/store/`（建表与只读检索在 `store.go`，
覆盖式写接口在 `admin.go`）。数据按**语言域 `lang` + 实体域 `Kind`** 两级切分。

## 1. 建库参数

```go
sql.Open("sqlite", path+"?_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)")
d.SetMaxOpenConns(1)   // 单写多读，避免 SQLITE_BUSY
```

- `Open` 会自动 `MkdirAll` 父目录（`internal/store/store.go:170`）。
- 每次操作套 30 秒 `context.WithTimeout`（`internal/store/store.go:324`）。
## 2. 表结构（实体表模板见 `internal/store/store.go:119`，其余见 `:143`）

### `item` / `npc` / `mob` —— 三张同构实体表

物品、NPC、怪物三个域**共用一套 schema、但各存一张表**（列完全一样），由 `Kind` 决定行落在哪张。
同表就会互相覆盖名称。建表用 `entityTable` 模板 + `entityDDL(kind)`（`internal/store/store.go:119`）
生成，表名只来自 `Kind.table()` 的白名单映射（`internal/store/store.go:63`）：

```sql
CREATE TABLE <item|npc|mob> (
  lang       TEXT NOT NULL,      -- 语言域，如 zh-CN
  id         TEXT NOT NULL,      -- 8 位零填充字符串，前导零有意义
  name       TEXT NOT NULL DEFAULT '',
  descr      TEXT NOT NULL DEFAULT '',
  category   TEXT NOT NULL DEFAULT '',
  info       TEXT NOT NULL DEFAULT '{}',   -- JSON 对象（map[string]string）
  has_name   INTEGER NOT NULL DEFAULT 0,
  has_info   INTEGER NOT NULL DEFAULT 0,
  edited     INTEGER NOT NULL DEFAULT 0,   -- 管理页手工改过：重载时默认受保护
  updated_at INTEGER NOT NULL,   -- Unix 秒
  PRIMARY KEY (lang, id)
);
CREATE INDEX idx_<t>_name ON <t>(lang, name);
CREATE INDEX idx_<t>_cat  ON <t>(lang, category);
```

`info` 恒为 `map[string]string` 序列化结果，**没有嵌套 JSON**：嵌套结构在扁平化时就变成了
失败即报错"X 的 info 不是合法 JSON"（`scanItem`，`internal/store/store.go:621`）。

用于统计覆盖度（`Stats` 里 `SUM(has_name*has_info)` 即"齐全"数，`internal/store/store.go:696`）。

> **迁移语义**：三张实体表都用 `CREATE TABLE IF NOT EXISTS`，旧库（只有一张 `item`）打开时
> 只是在 `init` 里多出 `npc`、`mob` 两张空表，**不动 `item` 的既有数据**。

### `wz_file` —— 增量指纹表

```sql
CREATE TABLE wz_file (
  lang TEXT NOT NULL, path TEXT NOT NULL,   -- path 相对 wz 根，正斜杠
  size INTEGER NOT NULL, mtime INTEGER NOT NULL,
  status TEXT NOT NULL,                     -- ok / failed
  err TEXT NOT NULL DEFAULT '',
  repaired INTEGER NOT NULL DEFAULT 0,      -- 补了多少个截断标签
  rows INTEGER NOT NULL DEFAULT 0,          -- 该文件贡献的条目数
  scanned_at INTEGER NOT NULL,
  ids TEXT NOT NULL DEFAULT '[]',           -- 文件级溯源：本文件贡献过哪些 `kind:id`
  PRIMARY KEY (lang, path)
);
```
指纹判定在 `Pending`（`internal/store/store.go:329`）：**没有记录，或 `size` 变了，或 `mtime` 变了** → 需要重解。
失败记录同样入库，便于排查与定向重跑（`status='failed'` + `err` 原因）。

（`contributedIDs`，`internal/scan/scan.go:361`）。每一项带**实体域前缀**，形如 `mob:00000021`（`tokenOf`，
`internal/store/admin.go:58`）——因为三个域共用 8 位 ID 空间，不带域前缀就无法判断"清掉这个文件的贡献"该动哪张表；
**裸 ID（无前缀）按物品解释**以兼容旧库（`parseToken`，`internal/store/admin.go:61`）。有了它才能回答"这个 XML 管着哪些实体"，
进而在文件内容变化后清掉**不再贡献**的旧贡献。**旧库该列为空**（`'[]'`），
此时逐文件重载只能覆盖本次解析到的字段，无法反查清除历史贡献——管理页会持续提示先跑一次全库强制重扫。

### `scan_run` —— 扫描历史

```sql
CREATE TABLE scan_run (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  lang TEXT NOT NULL DEFAULT '',
  started_at INTEGER NOT NULL, finished_at INTEGER,
  total INTEGER NOT NULL DEFAULT 0, parsed INTEGER NOT NULL DEFAULT 0,
  failed INTEGER NOT NULL DEFAULT 0, note TEXT NOT NULL DEFAULT ''   -- note = 参与扫描的 sources
);
```

`StartRun` 在解析前插一行拿 `runID`，`FinishRun` 回填收尾。用于回答"上次扫描跑了多久、处理了多少"。

## 3. 写入规则（两套语义）

### 3.1 扫描侧：只增不减（`PutNames` / `PutInfos`）
入参 `NameArg`（`internal/store/store.go:403`）与 `InfoArg`（`internal/store/store.go:466`）各带
`Kind`（决定行落哪张表，空按物品）与 `Src`（贡献文件路径，供落库定序用）。一批可以混装多个域，
`PutNames`/`PutInfos` 按**每行自己的 `Kind`** 分流到 `item`/`npc`/`mob` 各自的表（`Kind.table()`）。

| 方法 | 冲突动作 | 关键点 |
|---|---|---|
| `SaveFiles` | `ON CONFLICT(lang,path) DO UPDATE` 全字段刷新（含 `ids`） | 一个事务内 prepared stmt 循环；`ids` 按 `Kind` 加前缀 |
| `PutNames` | 只更新名称侧；`name`/`descr` **非空才覆盖**；`category` **库内为空才填**；`has_name=1` | 名称 trim 后为空的条目跳过且不计数 |
| `PutInfos` | `info` 先读旧值 **按 key 合并** 再整体写回；`category` 同上；`has_info=1` | `len(Info)==0` 的条目跳过 |

三条设计意图：

1. **两侧互不覆盖**——`Item.wz` 后到不会抹掉 `String.wz` 已写的名字，反之亦然。
3. **info 累积**——同一 ID 从多处补属性会合并（`mergeInfo`，`internal/store/store.go:514`；
   旧 JSON 解析失败时退化成空 map，即"用新值覆盖坏数据"而不是整条放弃）。
> **落库定序**：`scan` 在 flush 前对名称/属性批按 `(ID, Src)` 排序（`internal/scan/scan.go:178` / `:184`），
> 所以同一 ID 被多张表命中时胜者固定，不再取决于并发协程谁先跑完（修复前会随负载抖动）。

### 3.2 管理侧：以文件为准（`internal/store/admin.go`）

XML 里删掉一个字段、删掉一个条目时，3.1 的"只增不减"会让库里留着旧值。管理页的重载走另一套：

| 方法 | 语义 |
|---|---|
| `PutNamesForce` | 名称侧**整行覆盖**（`name`/`descr` 直接写入，空也写），并**清掉 `edited` 标记**；按行内 `Kind` 分流 |
| `PutInfosForce` | `info` **整包替换**（不再 merge），XML 里删掉的键这里就没了；`has_info` 随实际条数归位；按行内 `Kind` 分流 |
| `ClearSide(lang, refs, side, exceptPath, skipEdited)` | 文件不再贡献某些 `kind:id` 时，把那一侧清空（名称侧 `name=''`+`has_name=0`，属性侧 `info='{}'`+`has_info=0`） |
| `DeleteFiles(lang, paths, skipEdited)` | 删除文件记录，并连带 `ClearSide` 它**独占**的贡献 |
| `DiffFiles` | 磁盘指纹 ↔ `wz_file` 指纹，四态：`new` / `changed` / `gone` / `unchanged` |

两个保护规则，都是为了避免"重载把别人的数据也清了"：

- **归属保护**：`ClearSide` 前先统计该溯源在同侧还被哪些文件认领（`idOwners` 一次读全表 `ids`，
  归属以 **`kind:id` 串**计（`IDRef.String()`，`internal/store/admin.go:55`），
  所以清怪物的失效贡献绝不会碰到同 ID 的物品行（`groupByKind`/`clearRefs` 按域落到各自的表）。
- **手工保护**：`edited=1` 的行默认跳过（`skipEdited`），被跳过的条数计入 `Result.Protected`，
  管理页显示"跳过手工修改 N 条"。手工标记按实体域存在各自的表里，`EditedIDs(kind, …)` 只查该域的表，
  物品域改过的行不会保护怪物域同 ID 的行。勾掉「同时覆盖手工修改过的行」才会覆盖。
`DeleteMissing`（`internal/store/store.go:810`）现在只是 `DeleteFiles`（`internal/store/admin.go:564`）的包装：
先由 `DiffFiles` 的口径算出磁盘上已消失的路径，再按归属保护清理。
`scan` 只在**全库扫描**（未指定 `Paths`）时调用它，定向重载不做全局清理。

## 4. 旧库迁移（v1 无 `lang` 列 → v2）
`Open` 时自动执行 `migrateLegacy`（`internal/store/store.go:246`）：

```
对 item / wz_file 各做一遍：
  若表存在且无 lang 列：
    DROP INDEX idx_item_name; DROP INDEX idx_item_cat;   ← 必须先删，否则改名后同名索引挡住新表建索引
    ALTER TABLE t RENAME TO t_v1;
    执行 schema 建新表;
    INSERT OR IGNORE INTO t(lang, ...) SELECT 'zh-CN', ... FROM t_v1;
    DROP TABLE t_v1;
若 scan_run 存在且无 lang 列： ALTER TABLE ADD COLUMN lang TEXT NOT NULL DEFAULT ''
```
回填语言固定为 `LegacyLang = "zh-CN"`（`internal/store/store.go:31`），依据是"现有数据实测来自中文导出包"。
会补调一次 `entityDDL(KindItem)`（`internal/store/store.go:281`）。

### v2 → v3：补列（`item.edited`、`wz_file.ids`）+ 建实体表
`Open` 里 `init()`（`internal/store/store.go:170`）先迁移、再对 `Kinds` 里三个域各跑一遍
`entityDDL`（`CREATE TABLE IF NOT EXISTS`，所以旧库只多出 `npc`、`mob` 两张空表），最后逐列检查
（`hasColumn` 走 `PRAGMA table_info`）缺则 `ALTER TABLE ... ADD COLUMN ... DEFAULT`：

```
item.edited     INTEGER NOT NULL DEFAULT 0
wz_file.ids     TEXT NOT NULL DEFAULT '[]'
```

ADD COLUMN 带默认值不动数据，40 MB 级别的库瞬间完成；旧行读出来就是"无手工修改、无溯源"，
管理页据此提示先做一次全库强制重扫。新增列一律走这条路，不要再改建表语句就完事。

## 5. 检索条件构造（`Query.clauses`）
`internal/store/store.go:849`，全部走参数绑定，**不拼接用户输入进 SQL 文本**；表名由 `Query.Kind`
经 `Kind.table()` 白名单映射选出（`internal/store/store.go:63`）。

| 字段 | 生成条件 | 规则 |
|---|---|---|
| `Lang` | `lang = ?` | 必填，永远是第一个条件 |
| `IDPrefix` | `(id >= ? AND id < ?) OR (id >= ? AND id < ?)` | 前缀 < 8 位时**同时**查 `P*` 与 `0P*`；上界用 `prefixUpper`（`internal/store/store.go:918`）逐字节 +1，不用 `LIKE` 以便走主键 |
| `Name` | `name LIKE '%X%'` | 模糊 |
| `Category` | `category = ?` | 精确；`(未分类)`（`store.NoCategoryName`）翻译回 `category = ''` |
| `HasName` / `HasInfo` | `has_name = ?` | 三态：`nil` 不过滤 |
| `Wants` | `json_extract(info, '$."k"') = ?` | 只支持等值 |
| `GTE` / `LTE` | `json_extract(info, ?) IS NOT NULL AND CAST(json_extract(info, ?) AS INTEGER) >= ?` | 数值上下界；**先要求键存在**，缺该键的行不会被当成 0 命中（修复前用 `COALESCE(...,'0')` 会误命中无该属性的行） |
| `Has` | `json_extract(info, ?) IS NOT NULL` | 只要求键存在，不比值 |
**JSON 路径必须加双引号**：`jsonPath`（`internal/store/store.go:845`）把键包成 `$."icon.width"`，
并对 `"` 与 `\` 做转义。原因：真实键里有点（`icon.origin.x` 会被当成嵌套路径）和 `@`（`@indent`）。

`Limit` 归一到 `1..500`，缺省 50（`internal/store/store.go:558` `Search`）。

## 6. 统计口径

| 指标 | 定义 | SQL |
|---|---|---|
| `items` | 该**实体域 + 语言域**的实体总数 | `COUNT(*) FROM <kind>` |
| `named` | 有名称 | `SUM(has_name)` |
| `withInfo` | 有属性 | `SUM(has_info)` |
| `complete` | **齐全** | `SUM(has_name * has_info)` |
| `files` / `failed` | 指纹数 / 失败数 | `COUNT(*)` / `SUM(status='failed')`，是**语言域级别**、与 kind 无关 |
| `lastRunUnix` | 最近一次扫描开始时间 | `MAX(started_at)` |
| `langs` | 各语言域规模，按物品数降序 | `GROUP BY lang`（`Langs`，`internal/store/store.go:675`） |

## 7. 已知限制

1. **无全文检索**：`name LIKE '%X%'` 不走索引，三张实体表各自 27k / 万级行量下无感，再扩量需另议（如 FTS5）。
2. **`Wants` 只支持等值**；`GTE`/`LTE` 按域各自的 `info` 键生效（物品看 `reqLevel`、怪物看 `maxHP`），HTTP 侧 `min`/`max` 可重复传多条。
3. **`info` 无类型**：全是字符串，数值比较靠 `CAST`。
4. **`ids` 为空的老库无法精确清理**：重载会覆盖解析到的字段，但清不掉历史遗留的多余贡献，
   必须先跑一次全库强制重扫把溯源补齐。
5. **手工保护是整行粒度**：`edited=1` 同时挡住名称侧与属性侧的覆盖，做不到"只保留名字、属性照旧重载"；
   但保护是按实体域分表的，物品域的手工标记不会影响怪物域同 ID 的行。
6. 单写连接（`SetMaxOpenConns(1)`）意味着**并发扫描多个语言时互相排队**，`scan` 已经是逐语言串行调用。
