## 4. 图标覆盖（`imgdata/`，按域取图）

```bash
find imgdata -name '*.img.png' | wc -l                                    # 28,504（磁盘口径）
./bin/maplewzmeta.exe stats | head -1                                     # 图标索引：37,109 个文件，36,646 个可用 ID（Character=20681 Item=6590 Mob=1865 Morph=72 Npc=7465 Reactor=365 Skill=71）；按域 item=27266，npc=7465，mob=1865，skill=71，morph=72，reactor=365
tot=0; for off in $(seq 0 500 56500); do                                  # 物品域整表翻页数 icon 字段
  tot=$((tot + $(curl -s "http://127.0.0.1:8080/api/items?kind=item&limit=500&offset=$off" | grep -o '"icon":"' | wc -l)))
done; echo $tot                                                           # 20,635
```

| 指标 | 值 | 说明 |
|---|---|---|
| 磁盘图片 | 37,109 | 归档 `imgdata.zip` 内条目：`Character` 20,681 / `Npc` 7,465 / `Item` 6,590 / `Mob` 1,865 / `Reactor` 365 / `Morph` 72 / `Skill` 71 |
| 进入索引的文件 | 37,109 | 归档内条目名均为纯数字 `.img.png`，无一被拒 |

**复查判据**（任一条不成立即说明串味复发）：

```bash
curl -o /dev/null -sw '%{http_code}\n' "http://127.0.0.1:8080/img/09000001.png"           # 404 —— 物品域不认 Npc 图
curl -o /dev/null -sw '%{http_code}\n' "http://127.0.0.1:8080/img/09000001.png?for=npc"   # 200 —— NPC 域认
curl -s "http://127.0.0.1:8080/api/items?kind=npc&limit=500" | grep -c '"icon":"/img/[0-9]*.png?for=npc"'   # >0 —— NPC 行的图标 URL 一律带 for=npc
curl -s "http://127.0.0.1:8080/api/items?kind=mob&limit=500"  | grep -c '"icon":"'                          # 0 —— 怪物行一律无图标（icon 为空时字段整个省略）
```

历史口径对照：旧版"22,165 行带图标"（39.40%）里有 **1,578 行（7.1%）的图标其实来自 `Npc` 域**
（`Character` 20,278 / `Item` 306），取样 `00002003`、`00012000`、`09000001` 当时都显示 NPC 立绘；
根因是 `Npc.wz` 的 ID 与物品 ID 重叠 1,806 个、`Mob.wz` 重叠 1,861 个，而旧的跨域优先级
"装备图优先"挡不住"该 ID 没有装备图、于是拿 NPC 立绘顶上"。现在这些行不再挂图（`item` 域查不到即无 `icon`），
详见 [附录-实体与String.wz的关联](附录-实体与String.wz的关联.md) §6。

坑：`01102670 .img.png`（词干带**尾随空格**）能被索引，因为 `NormalizeID` 先 `TrimSpace`。
导出器偶发产生这类文件名，改 `Build` 的过滤时注意别把它们全丢掉。

## 6. 本轮修复的缺陷（附修复方式与复查判据）

四件都源自同一件事：把解析从"只有物品"扩到 **物品 / NPC / 怪物** 三个实体域。
落点是 [附录 §7](附录-实体与String.wz的关联.md) 那张按性价比排的清单里的 1~5 项。

### 6.1 名称侧跨实体表污染（**已修复**）

**现象（历史口径，2026-09-21）**：`scan` 的分流判据只是"相对路径以 `String.wz` 开头 → 名称侧"，
于是 `String.wz` 下**每一张表**都按物品名称入库。其中三张属别的实体域：

| 文本表 | 带 `name` 的 7/8 位 ID 条目 | ID 实际含义 | 补零后落入的 item 语义 |
|---|---|---|---|
| `String.wz/Mob.img.xml` | 2,002 | 怪物 ID（`1110100` 绿蘑菇） | `0111xxxx` = 戒指号段 |
| `String.wz/Npc.img.xml` | 1,803 | NPC ID | `0100xxxx`/`0101xxxx` = 帽子/饰品号段 |
| `String.wz/Skill.img.xml` | 542（7 位 360 + **8 位 182**） | 技能 ID | 与 `Etc`/`Consume`/`Cash` 号段大面积重叠 |

合计 **4,347 条**、占当时名称条目（28,260）的 **15.4%**，且**污染面是 100%**——
三张表的键补零后与当时库内 56,264 个物品 ID 逐一比对，2,002 / 1,803 / 542 全部命中：
物品 ID 空间被各实体域整体复用，不存在"错开号段"的保护（附录 §4.1 有逐表贡献全表）。
统计侧当时的可观测症状：名称条目 28,262 → 唯一 ID 27,696，**566 个 ID 被跨表重复写名**；
`仅有名称`（4,733）里相当一部分根本不是物品，而是怪物/NPC/技能。
更糟的是**胜者不固定**：同一 ID 被多张表命中时，落库结果取决于并发解析的到达顺序
（当时 `internal/scan/scan.go` 的多协程 fan-out + 单消费者按到达顺序攒批），
本机三次重扫恰好稳定，但文件数或机器负载一变即可能翻转——这也是"定序落库"必须和白名单同做的原因。

**修复方式**：

| 环节 | 做法 | 落点 |
|---|---|---|
| 分流 | 名称侧改成**表名白名单** `表名 → 实体域`：`Cash/Consume/Eqp/Etc/Ins/Pet` → item、`Mob` → mob、`Npc` → npc，其余 12 张整份跳过 | `internal/extract/extract.go:83`、判定 `:98`、闸门 `internal/scan/scan.go:327` |
| 落库 | 三个域各一张表 `item`/`npc`/`mob`，行归属由 `scan` 从路径推导，存储层不再自己判路径 | `internal/store/store.go:63`、DDL `:138`、`internal/extract/extract.go:105` |
| 幂等 | 同 ID 多文件命中时胜者由 `(ID, 来源路径)` 定序，不再取决于并发到达顺序 | `internal/scan/scan.go:178`、`:184` |
| 旧数据 | 一次性清残留：物品域 `has_name=1` 但没有任何名称侧文件的 `item:<id>` 溯源认领 → 抹名 | 本机实清 **3,791 行**，判据全文见附录 §4.2 |

评估过的替代方案里，"按 ID 段过滤"**不可靠**（附录 §4 已证 ID 空间被实体域整体复用），
"加 `name_source` 列只告警"不消除污染，都被否掉；选表白名单 + 分域落库。

**复查判据**：

```bash
./bin/maplewzmeta.exe query -id 01110100             # 物品域：无名称（旧值"绿蘑菇"）
./bin/maplewzmeta.exe query -kind mob -id 01110100   # 怪物域：绿蘑菇
./bin/maplewzmeta.exe query -id 04000000             # 蓝色蜗牛壳（旧值"集中术"，Skill 表灌的）
./bin/maplewzmeta.exe query -id 08220016             # 无名称：Mob.wz 里根本没有这个怪物包
# 无主名称残留必须为 0：物品域 has_name=1 却在名称侧溯源里认领不到 item:<id> 的行
```
零污染的结构保证：`/api/admin/sources?kind=item&id=<id>` 对任何物品行都**不会**列出
`String.wz/{Mob,Npc,Skill}`——`Skill` 表根本不入库，`Mob`/`Npc` 写进的是别的表。

### 6.2 Hair/Face 缺名称（**已修复**）

**现象（历史口径）**：物品缺名称 28,568 条里 Hair 15,234 + Face 9,555 占 87%，
曾被定性为"导出范围问题"。实测证伪：它们的名称就写在 `String.wz/Eqp.img.xml` 里，
只是那 22,725 个条目用 **5 位 ID**（只落在 `Hair` 13,366 / `Face` 9,359 两组），
被当时 `LooksLikeItemID` 的"7 或 8 位"判据整批丢弃；`NormalizeID` 本身支持 5 位补零，门槛只在识别层。

（`internal/extract/extract.go:123`）——物品仍是 7/8 位，**只在 `table == "Eqp"` 时另放 5 位**
（`internal/extract/extract.go:135`）；NPC/怪物则放宽到 1~8 位皆可
（`Mob.wz/0000021.img.xml` 与 `String.wz/Mob` 里的 2 位键 `21` 是同一个怪物，两侧都得认）。
5 位之所以不敢全局放宽：会顺手把 `Mob` 的 6 位、`Npc` 的 3~5 位键放进来，必须先有 6.1 的白名单。

**复查判据**：`query -id 00020000` = 酷-男脸(黑色)（Face）；物品有名称 27,696 → **46,628**、
齐全 22,963 → **45,958**（与预测的"涨到约 45,654"同量级，差额来自清污与新增行）；
`String.wz/Eqp.img.xml` 里 5 位键仍只出现在 Hair/Face 两组（附录 §8 那条 perl 命令）。

### 6.3 `Item.wz/Pet` 属性漏抽（**已修复**）

**现象（历史口径）**：宠物道具（`0500xxxx`）**只有名称、没有属性**——
`Item.wz/Pet/<7位>.img.xml` 是"文件名即 ID、没有内层 imgdir"的形态，
而当时 `extract.Infos` 的"根名即 ID"特判只对 `Character.wz` 开，`query -cat Pet` 命中 0 条。
**修复方式**：`extract.RootID`（`internal/extract/extract.go:328`）改为
**要求文件名与根 imgdir 名同为数字 ID 且位数 ≥ 7**（`internal/extract/extract.go:334`），
不再按包名开特判，`Infos` 一律先试它（`internal/extract/extract.go:216`）。
于是 `Mob.wz` / `Npc.wz` / `Item.wz/Pet` / `Character.wz` 四条路径全部走这条路；
`Item.wz/Etc/0430.img.xml` 这类**根名同为数字但只有 4 位**的分组文件仍被位数门槛挡在外面、继续走内层键。
"文件名 == 根 imgdir 名"这半个条件不能省：只看位数的话分组文件会被当成单实体，把整文件属性挂到错 ID 上。

**复查判据**：`query -cat Pet` 有命中（修复前 0 条）；`query -id 05000000` = 褐色小猫**且带属性**；
`query -id 04000000` 的属性仍来自 `Item.wz/Etc/0400.img.xml` 的内层键（4 位分组文件没被误判成单实体）。

### 6.4 图标域串味（**已修复**）

**现象（历史口径）**：`icons.Build` 跨域按 `Item`=0 > `Character`=1 > 其他=5 去重后，
拿一把 ID join 回物品行，22,162 行命中里有 **1,578 行（7.1%）的图标其实来自 `Npc` 域**——
`rankOf` 只保证装备图优先，挡不住"该 ID 没有装备图、于是拿 NPC 立绘顶上"。

**修复方式与判据**：见 §4 的"串味已修"段（`(域, ID)` 索引 + `entityDomains` 白名单 + `/img?for=`），
四条 curl 判据任一不成立即说明复发。

**顺带一条实测事实**：`imgdata/` 没有 `Mob` 目录，所以怪物域可取图 ID = **0**、怪物行一律无图标，
这是导出范围问题不是索引坏了（§5 已列为缺口）。

### 6.5 管理页偶发滚不动（**已修复**）

**现象**：在 `/admin` 里做比对 / 查询 / 触发重载任务后，页面偶发滚不动或滚动回弹，
**关闭标签页重新打开即恢复**。代码层面 CSS/DOM 无 `overflow:hidden`、无固定高度、无 `wheel` 拦截，
内置 Chromium 实测 `scrollTo` 正常——典型的"运行时状态污染、reload 清除"特征。

**根因**：管理页会频繁整体替换表格 `innerHTML`（`doDiff`/`doFiles`/`pollJob` 每 1.2s 刷新），
当被替换的内容位于当前视口上方时，Chromium 的**滚动锚定（scroll anchoring）**会主动补偿 `scrollY`
以保持视觉稳定；高频重绘下偶发把用户滚动"锁"在原位或回弹，重新加载会清空锚定状态故恢复。

**修复方式**：`admin.html` 的 `html { overflow-anchor: none; }` 关闭整页滚动锚定。
**复查判据**：`getComputedStyle(document.documentElement).overflowAnchor === 'none'`，
且加载长表后 `window.scrollTo(0,700)` 能改变 `scrollY`（内置浏览器已实测两项均通过）。

## 8. 辅助命令

| 命令 | 用途 |
|---|---|
| `cmd/wzstats` | 全量解析但不落库，输出规模/耗时/类型统计，用来验证解析内核 |
| `cmd/wzbind` | 名称+属性关联覆盖率验证，只读内存 |

两者是**验证工具**，不参与正式链路；改动抽取逻辑后先跑它们，再决定是否重扫。
注意 `wzbind` 的默认源仍是物品侧那三个包（`-sources String.wz,Item.wz,Character.wz`），
**不分实体域**——三个实体域链路的验证走 `scan` + `stats`（§2），别拿它当三域基线。
