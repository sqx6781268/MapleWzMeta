# 01 · 架构与实现路径

## 1. 项目目标

构建 **实体 ID + 名称 + 属性** 三位一体的元数据库，并提供低成本检索手段。当前覆盖
**物品 / NPC / 怪物三个实体域**（`Kind` = `item` / `npc` / `mob`），三个域共用同一条解析管线、
各自入同构的一张表。核心难点不在"解析 XML"，而在**同一个实体的信息分散在多个 .wz 包、且层级不一致**
（详见 [04-物品ID与关联规则](04-物品ID与关联规则.md)），因此整条管线以"ID 归一化 + 两侧 upsert 合并"为主轴，
并在入口处按"来源 + 位数形态"把每条记录归到正确的实体域。

## 2. 模块与依赖方向

```
cmd/maplewzmeta  ──┬── internal/config    读 wzconfig.json
                   ├── internal/scan       管线编排（唯一串起下面所有包的地方）
                   ├── internal/web        HTTP + go:embed 内置页
                   └── internal/icons      图片索引与 /img 供给
cmd/wzstats      ─── internal/wzxml        只做规模统计，不入库
cmd/wzbind       ─── internal/{wzxml,extract,binder}  只做内存关联，不入库

internal/scan    ──→ internal/{wzxml, extract, store}
internal/store   ──→ (database/sql + modernc.org/sqlite)
internal/binder  ──→ internal/extract   （仅被 cmd/wzbind 使用）
```

依赖是**单向、无环**的：`wzxml` 不知道 `extract` 存在，`extract` 不知道 `store` 存在，
（`internal/wzxml/node_test.go:420` 的 `TestRealTreeSample` 直接读 `wz/` 里的真实文件）。

## 3. 数据管线（六阶段）

| 阶段 | 实现 | 做什么 | 关键规则 |
|---|---|---|---|
| ① 收集 | `internal/scan/scan.go:453` `collect` | 按 `sources` 遍历目录，收 `*.xml`，记 `size + mtime` | 相对路径一律 `filepath.ToSlash`，全链路用 `/`；`sources` 里没导出的目录直接跳过，不报错 |
| ② 增量判定 | `internal/store/store.go:329` `Pending` | 与 `wz_file` 表里的指纹比对，只留下"新增或变了"的 | 指纹 = size + mtime(Unix)；导出器保留了源时间戳，robocopy 不破坏；`-force` 或管理页重载跳过这步 |
| ③ 解码 | `internal/wzxml/repair.go:35` `DecodeFileRobust` | BOM/编码归一 → 严格解码 → 失败再补截断标签 | 修复只在内存副本，**绝不回写源文件** |
| ④ 打平 uol | `internal/wzxml/uol.go:28` `ResolveUol` | 把 `<uol>` 换成目标子树深拷贝 | 父相对优先、根相对兜底、最多 16 趟、目标缺失保留原样 |
| ⑤ 抽取 + 定域 | `internal/extract/extract.go:158` `Names` / `:216` `Infos` | 认出 ID 节点、摊平 `info`，并判定实体域 `Kind` | 名称侧按 `String.wz` **表名白名单** `nameTables`（`internal/extract/extract.go:77`）定域，不在白名单里的表整份跳过；属性侧按包名 `KindOf`（`internal/extract/extract.go:99`）定域；分流见 `internal/scan/scan.go:330`（名称侧）/ `:342`（属性侧） |
| ⑥ 落库 | 累积：`internal/store/store.go:427` `PutNames` / `:483` `PutInfos`；以文件为准：`internal/store/admin.go:351` `PutNamesForce` / `:402` `PutInfosForce` | 按 `(lang, id)` upsert 进对应域的表 | 每行按自身 `Kind` 分流到 `item`/`npc`/`mob` 表；累积模式两侧互不覆盖空值、`info` 按 key 合并；覆盖模式整包替换并清掉该文件不再贡献的 ID（`ClearSide`），两种都保护 `edited=1` 的手工行 |
⑥ 落库前对名称/属性批按 `(ID, Src)` 排序（`internal/scan/scan.go:178` / `:184`），同一 ID 被多张表命中时
（如 `mob:00000021`）写进 `wz_file.ids`（文件级溯源，`internal/store/admin.go:58` `tokenOf`），
收尾：`FinishRun` 记一次扫描结果，`DeleteMissing`（`internal/store/store.go:810`）清掉磁盘上已不存在的文件指纹
——它现在会连带清掉那些文件**独占**的贡献（`internal/store/admin.go:564` `DeleteFiles`），
且只在未指定 `Paths` 的全库扫描时执行。

`entityDomains`（`internal/icons/icons.go:34`）把物品限定在 `{Item, Character}`、NPC 在 `{Npc}`、怪物在 `{Mob}`，
物品行因此不会拿到 NPC 立绘（修复前实测 1,578 行串味，见 [附录-实体与String.wz的关联](附录-实体与String.wz的关联.md) §6）。

## 4. 并发与批处理模型

```
      ┌── worker 1 ──┐
entry →   worker 2   → fileOut(带锁外的单消费者) → 攒够 batch(默认400) → 一次事务落库
      └── worker N ──┘
```
- `workers <= 0` 时取 `runtime.NumCPU()`（`internal/scan/scan.go:87`）。
- **解析并发、落库单线程**：结果通过 `out` 通道由一个 goroutine 串行消费（`internal/scan/scan.go:241`），
- SQLite 侧同样 `SetMaxOpenConns(1)`（`internal/store/store.go:181`）：单写多读，配合
  `busy_timeout(10000)` + `journal_mode(WAL)` + `synchronous(NORMAL)` 避免 `SQLITE_BUSY`。
- 通道缓冲 512，批次默认 400 个文件一提交（CLI `-batch` 可调）。

实测全量首扫 45,592 个物品相关文件约 38 秒；重跑时因指纹未变，几乎即时。

## 5. 三个入口的分工

| 命令 | 入口 | 用途 | 是否写库 |
|---|---|---|---|
| `maplewzmeta` | `cmd/maplewzmeta/main.go:41` | 正式工具：`scan / query / stats / serve` | `scan` 写，其余只读 |
| `wzstats` | `cmd/wzstats/main.go:92` | 全量规模体检：节点数、深度、类型分布、uol 解析率、失败清单 | 否 |
| `wzbind` | `cmd/wzbind/main.go:30` | 全量内存关联：验证 ID 对齐到底覆盖多少 | 否 |

`wzstats` / `wzbind` 是**验证内核**，不参与交付；改了 `wzxml` 或 `extract` 后先跑它们，再跑 `scan`。

## 6. 技术取舍（有意为之，勿轻易推翻）

| 选择 | 原因 |
|---|---|
| 纯 Go，`modernc.org/sqlite` 而非 `mattn/go-sqlite3` | **本机没有 gcc/cgo 工具链**，cgo 驱动根本编译不了；`-race` 同样不可用 |
| 标准库 `net/http` 的 `ServeMux` 方法路由 + `flag` 子命令 | 不引 gin/cobra/viper/zap；查询层只需要 JSON 端点 + 一张表页 |
| `go:embed internal/web/static/index.html` | 单二进制交付，不需要前端构建链；要做 Vue 版界面（第三阶段）需先确认可行性 |
| 只支持 `wzconfig.json`（带 `//` 行注释） | 全是结构化字段，标准库 `encoding/json` 够用 |
| 自研确定性 JSON（`_t/_n/_v/_o/_a/_c`） | 键序固定才能做 golden 对比；且要能原样保存 WZ 里的非法 UTF-8 字节 |
| 解析器不做属性白名单 | 各导出器属性集不一致，除 `name/value` 外的属性一律进 `Node.Attrs` 原样保留 |
| 三个实体域**分表**而非同表加 `kind` 列 | 实测怪物/NPC 的 ID 补零到 8 位后与物品 ID 空间**整体重叠**（Mob 2,002、Npc 1,803 条名称 100% 落在物品行上），同表就是互相覆盖；三张同构表列完全一致，只靠 `Kind` 选表（详见 [06](06-数据模型与存储规则.md) §2） |
| 不做 BeiDou 式"整文件中英覆盖合并" | 对照外部笔记（BeiDou gms-server 的 `LocalizedDataProvider`：语言目录有同名 xml 就整份用它、缺文件才回退英文基础）后确认本机 no-op：`wz-zh-CN/` 只导出了 41 个 XML，抽查 `String.wz/{Mob,Npc,Eqp}.img.xml` 与 `wz/` 同名文件 **md5 完全相同**；真要接第二门语言时按 `locales` 各扫各的即可，无需在解析层加合并。笔记里的 `getChildByPath` 逐段寻址 + `..` 回跳，本项目的 uol 展开已覆盖同等能力（详见 [07](07-配置文件说明.md) §6） |

## 7. 全局不变量

1. **实体 ID 在库内恒为 8 位定长字符串**，前导零有意义，禁止转成整数；`NormalizeID` 是唯一的补齐入口。
2. **一切数据按 `lang` + `Kind` 两级分域**：`item`/`npc`/`mob`/`wz_file` 主键都以 `lang` 打头，实体域则决定行落在哪张同构表；换语言或换域都不覆盖已有行。
3. **图标与语言无关、但按实体域取用**：只在内存建索引，不落库；`/img/<id>.png` 用 `?for=<kind>` 决定允许的来源目录（缺省即物品域）。
4. **溯源串带实体域前缀**：`wz_file.ids` 每项形如 `mob:00000021`，裸 ID 按物品解释以兼容旧库。
5. **源文件只读**：任何修复、归一、打平都只发生在内存副本。
6. **`wz/` 路径与 DB 路径的基准是配置文件所在目录**，与进程启动目录无关。
7. 未识别/解析失败**不静默丢弃**：失败原因写进 `wz_file.err`，未解析 uol 由 `wzstats` 报出来。
